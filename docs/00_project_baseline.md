# 项目宪章

本文件是校园二手交易系统的最高项目口径。它只回答项目为什么存在、正式做什么、不做什么、采用哪些长期架构和治理选择。

产品入口、页面和用户旅程见 `01_project_shape.md`；角色权限、领域对象、接口族、事件和一致性规则见 `02_domain_contracts.md`；数据库结构见 `05_database_design.md`；最终验收检查见 `04_final_quality_criteria.md`。

## 项目使命

本项目是一个面向校内用户的可信校园二手交易平台。

系统按单校部署设计，学校名称、校区、院系、邮箱后缀、地点字典和商品分类等作为配置数据维护；不把多学校运营、跨校商户体系或外部学校统一身份认证作为运行前提。

系统目标不是“前端页面加后端接口加数据库表”，而是让校园身份、可信商品、站内协商、担保式在线支付、线下面交、评价信用、举报治理和商品发布辅助形成完整交易闭环。

## 成功定义

项目达到目标形态时，应能支撑一笔校内二手交易从可信身份到治理留痕的完整生命周期：

```text
校园认证
  -> 商品发布与 AI 发布辅助
  -> 商品审核与上架
  -> 搜索推荐与商品发现
  -> 站内会话与议价协商
  -> 订单创建、商品占用与卖家确认
  -> 担保支付、托管与支付回调
  -> 线下面交、完成确认与卖家结算
  -> 评价信用
  -> 举报申诉与后台治理
  -> 通知公告、统计审计与隐私留痕
```

成功不以页面数量、接口数量或表数量衡量，而以交易事实是否可追溯、资金状态是否清晰、治理动作是否留痕、用户隐私是否受控为准。

## 核心价值

- 用校园认证降低陌生交易的信任成本。
- 用商品审核、图片材料、分类标签和发布规范提升商品可信度。
- 用站内会话、订单状态、支付状态和治理记录保留交易证据。
- 用担保式在线支付、托管、结算和退款形成可追溯资金链。
- 用评价、信用、举报、申诉和处罚记录形成治理闭环。
- 用 AI 商品发布助手和审核预检提升信息质量，同时控制算力与 token 成本。
- 用 Spring Boot、React、PostgreSQL 和 Docker 化部署形成可复现工程环境。

## 目标能力

| 能力 | 项目级目标 |
| --- | --- |
| 校园身份与权限 | 用户基于校园身份建立可信交易资格，普通用户不可绕过认证进入完整交易。 |
| 商品可信发布 | 商品信息、图片、分类、标签、成色、价格和交易安排进入审核与上架流程。 |
| AI 发布辅助 | AI 只作为商品发布与审核预检的辅助能力，帮助优化标题、描述、分类、标签和预检提示。 |
| 商品发现与互动 | 用户可以通过搜索、分类、筛选、推荐、收藏、关注和公开留言发现商品。 |
| 站内协商 | 买卖双方围绕商品在站内完成消息沟通、议价和面交安排，并保留证据链。 |
| 面交订单 | 订单表达买家、卖家、商品、金额、面交安排和状态历史。 |
| 支付结算退款 | 在线支付采用担保式交易口径，支付、托管、结算、退款和异常处理均可追溯。 |
| 评价信用 | 交易完成后形成评价和可解释信用记录，不对普通用户展示单一黑箱信用分。 |
| 举报申诉治理 | 用户可以举报商品、留言、消息、订单或账号，管理员处理后支持申诉复核。 |
| 通知统计审计 | 站内通知、公告、后台统计、管理员操作日志和敏感访问日志构成运行闭环。 |

## 角色口径

| 角色 | 项目级定义 |
| --- | --- |
| 游客 | 未登录访问者，只能接触公开商品和公开信息。 |
| 注册用户 | 已注册但未完成完整交易认证的用户，可以维护资料、提交认证、收藏公开商品和提交举报。 |
| 认证学生 | 达到完整交易资格的主要交易用户，可以发布、协商、下单、支付、评价、举报和申诉。 |
| 内容管理员 | 负责日常内容审核、交易治理、举报申诉处理和统计查看。 |
| 超级管理员 | 负责系统级治理、角色配置、系统配置、敏感规则和关键审计。 |

买家和卖家不是独立账号类型，而是认证学生在特定商品、会话或订单中的上下文角色。详细权限矩阵以 `02_domain_contracts.md` 为准。

## 架构选择

| 层级 | 项目级选择 |
| --- | --- |
| 后端 | Spring Boot 模块化单体，承载认证、商品、订单、支付、文件权限、治理、通知统计和 AI 服务编排。 |
| 前端 | React 承载学生前台、卖家工作台和管理后台。 |
| 数据库 | PostgreSQL 保存业务事实、状态历史、审计记录、搜索索引支撑数据和统计视图。 |
| 文件 | 文件二进制进入统一文件存储层，Docker 环境优先采用 MinIO 或 S3 兼容对象存储；数据库只保存文件元数据和访问引用。 |
| 支付 | 使用模拟支付渠道作为正式运行能力，并保留真实支付适配器接口。 |
| AI | 通过内部 Intelligence API 按需调用；规则服务为主路径，LLM 为可选优化项。 |
| 接口 | 主接口采用 REST JSON，实时消息采用 WebSocket。 |
| 安全会话 | 登录态通过 HttpOnly Cookie 承载，服务端保存会话并采用滑动续期；WebSocket 握手复用同一登录态；不采用 access/refresh token 刷新体系。 |
| 配置 | 业务阈值进入系统配置并留痕；数据库、对象存储、支付、邮件、AI 和 HTTPS 证书等基础设施配置通过环境变量或外部配置注入。 |
| 部署 | 系统部署在公网云服务器，使用 Docker Compose 编排前端、后端、数据库和文件存储依赖，并配置域名与 HTTPS。 |

## 长期原则

- 校园身份是交易信任的入口；完整交易能力必须由认证和审核共同决定。
- 商品、订单、支付、结算、退款、评价、信用、举报、申诉、处罚、审核和审计等事实记录长期保留，不做简单物理删除。
- 在线支付采用担保式交易。支付成功表示资金进入托管状态，不表示卖家已收款。
- 系统不提供平台余额或钱包；每笔订单独立形成支付、托管、退款和结算记录。
- AI 只进入商品发布和审核预检链路，输出只作为建议或预检标签，不自动下架、封禁、扣信用或裁决申诉。
- 推荐、信用、治理和统计必须能解释来源，不使用无来源的黑箱结论。
- 私信正文、举报材料、申诉材料、认证材料和身份隐私资料不得进入推荐评分。
- 管理员是认证、商品审核、举报处理、申诉复核和权益影响动作的最终裁决者。
- 管理员访问认证材料、举报证据、申诉材料和私信内容等敏感材料时必须形成敏感访问日志。
- 订单占用、支付回调、定时任务、结算推进和退款处理必须具备幂等与一致性保护。
- 公网部署强制 HTTPS，运行密钥和外部服务配置不得固化在镜像中。

## 对象存储口径

对象存储沿用 MinIO 或 S3 兼容服务方案。Docker 环境使用 MinIO 作为本地对象存储依赖；后端只通过统一文件存储层访问对象存储，不把具体供应商写入领域对象。

实现上需要完成以下事项：

- 在 Docker Compose 中提供 MinIO 服务、持久化 volume、访问密钥、默认 bucket 和健康检查。
- 后端通过环境变量读取对象存储 endpoint、bucket、access key 和 secret key。
- 数据库只保存文件元数据和访问引用，包括 bucket、object key、原始文件名、MIME 类型、大小、校验值、文件类型、所属业务对象、上传者、审核状态和可见范围。
- 文件上传必须校验大小、MIME 类型和文件头，图片字段拒绝可执行格式。
- 商品图片在商品审核通过并公开上架后可以公开访问；私信图片、认证材料、举报证据、申诉材料和支付异常材料默认私有。
- 私有文件访问通过后端鉴权后生成临时访问地址，不能把长期公开 URL 直接落库。
- 管理员访问认证材料、举报证据、申诉材料和私信内容等敏感材料时，必须形成敏感访问日志。
- 对象存储需要纳入备份、容量监控和过期清理；孤儿文件清理任务必须幂等执行。

## 正式边界

本项目覆盖校园内 C2C 二手交易闭环，并包含担保式在线支付、支付状态同步、结算和退款处理。以下内容不进入正式目标边界：

- 快递物流、跨城配送和商业化寄卖。
- 多学校商业运营、商家入驻和广告投放。
- 让外部学校统一身份认证成为系统运行前提。
- 真实微信、支付宝或银联商户入网、真实资金清算和公网支付回调部署。
- 面向多商户平台的复杂分账、批量结算和财务清算系统。
- 让 AI 自动下架商品、自动封禁用户或自动裁决申诉。
- 原生 App、小程序或多端统一发布。

## ADR 粒度

ADR 只记录会改变长期架构、模块边界、核心状态机、资金链路、治理链路、AI 使用边界、核心领域对象或关键一致性约束的分叉决策。

单个字段名、页面交互、接口路径、提示文案、局部校验顺序、提醒样式和可由正式文档推导出的普通规则，不再单独创建 ADR。

历史访谈形成的细粒度 ADR 已被正式文档吸收，保留在 `docs/adr/archive/` 作为来源记录，不作为日常阅读入口。

## 正式口径

项目正式口径是：

> 一个以校园认证为信任基础、以担保式在线支付和线下面交为交易场景、以 AI 商品发布助手和审核预检为辅助能力、以评价信用和平台治理为闭环保障的校园二手交易系统。

系统数据模型负责保存事实、约束状态和追溯历史；业务流程负责让这些数据形成真实交易闭环；AI 能力负责改善商品发布质量并降低审核压力。
