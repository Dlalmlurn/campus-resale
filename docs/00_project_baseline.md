# 项目开发基准

本文件是校园二手交易系统的合成基线。它吸收已确认的产品边界、核心决策和长期约束，作为后续开发、接口、数据模型和页面设计的最高口径。

正式阅读优先级为：本文件、产品形态、领域契约、数据库设计、最终质量标准。ADR 只记录少数会改变长期架构或数据链路的分叉决策，不再为普通细则单独开文件。

## 项目定位

本项目是一个面向校内用户的可信校园二手交易平台。

系统按单校部署设计，学校名称、校区、院系等作为配置项维护；不把多学校运营、跨校商户体系或外部学校统一身份认证作为运行前提。

系统目标不是“前端页面加后端接口加数据库表”，而是围绕校园身份、可信商品、站内协商、担保式在线支付、线下面交、评价信用、举报治理和商品发布辅助形成完整交易闭环。

核心价值：

- 用校园认证降低陌生交易的信任成本。
- 用商品审核、图片材料、分类标签和发布规范提升商品可信度。
- 用站内会话、订单状态、支付状态和治理记录保留交易证据。
- 用担保式在线支付、托管、结算和退款形成可追溯资金链。
- 用评价、信用、举报、申诉和处罚记录形成治理闭环。
- 用 AI 商品发布助手和审核预检提升信息质量，同时控制算力与 token 成本。
- 用 Spring Boot、React、PostgreSQL 和 Docker 化部署形成可复现工程环境。

## 正式主线

```text
校园认证
  -> 商品发布与 AI 发布辅助
  -> 商品审核与上架
  -> 搜索推荐与商品发现
  -> 站内会话与议价协商
  -> 订单创建、商品占用与卖家确认
  -> 担保支付、托管与支付回调
  -> 线下面交、完成确认与卖家结算
  -> 评价信用
  -> 举报申诉与后台治理
  -> 通知公告、统计审计与隐私留痕
```

## 角色边界

| 角色 | 定义 | 核心能力 |
| --- | --- | --- |
| 游客 | 未登录访问者。 | 浏览公开商品、搜索公开信息。 |
| 注册用户 | 已注册但未完成校园认证的用户。 | 维护资料、提交认证、收藏公开商品、查看公告、提交举报。 |
| 认证学生 | 达到完整交易认证阈值并通过审核的主要交易用户。 | 发布商品、私信协商、创建订单、支付、评价、举报、申诉。 |
| 内容管理员 | 负责日常内容和交易治理。 | 审核认证和商品、处理举报申诉、管理分类标签、查看统计。 |
| 超级管理员 | 负责系统级治理。 | 管理角色、敏感规则、系统配置、关键审计和敏感访问日志。 |

买家和卖家是认证学生在特定商品或订单中的上下文角色。

## 技术基线

| 层级 | 口径 |
| --- | --- |
| 后端 | Spring Boot 模块化单体承载认证、商品、订单、支付、文件权限、治理、通知统计和 AI 服务编排。 |
| 前端 | React 承载学生前台、卖家工作台和管理后台。 |
| 数据库 | PostgreSQL 保存业务事实、状态历史、审计记录、搜索索引支撑数据和统计视图。 |
| 文件 | 文件二进制进入统一文件存储层，Docker 环境优先采用 MinIO 或 S3 兼容对象存储；数据库只保存文件元数据和访问引用。 |
| 支付 | 使用模拟支付渠道作为正式运行能力，并保留真实支付适配器接口。 |
| AI | 通过内部 Intelligence API 按需调用；规则服务为主路径，LLM 为可选优化项。 |
| 接口 | 主接口采用 REST JSON，实时消息采用 WebSocket。 |
| 安全会话 | 登录态通过 HttpOnly Cookie 承载，服务端保存会话并采用滑动续期；受保护请求刷新最后活跃时间，默认闲置上限为 7 天、绝对上限为 30 天；WebSocket 握手复用同一登录态；管理员账号采用单端登录策略；不采用 access/refresh token 刷新体系。 |
| 配置 | 业务阈值进入系统配置表并留痕，数据库、对象存储、支付、邮件、AI 和 HTTPS 证书等基础设施配置通过环境变量或外部配置注入。 |
| 部署 | 系统部署在公网云服务器，使用 Docker Compose 编排前端、后端、数据库和文件存储依赖，并配置域名与 HTTPS。 |

运行配置通过环境变量或外部配置注入，不能把数据库密码、支付配置或 AI 配置写死在镜像中。

## 长期约束

### 校园认证

- 未达到完整交易认证阈值并通过审核的用户不能发布商品、私信卖家、创建订单、支付或评价。
- 用户公开页只呈现昵称、认证标识、信用摘要和用户选择公开的院系信息；姓名、学号、手机号和认证材料不对普通用户公开。
- 校园认证采用 100 分制：姓名和学号 40 分，院系信息完整 10 分，校园邮箱验证 10 分，学生证或校园卡材料审核通过 40 分。
- 认证可信度达到 50 分进入管理员审核队列；开放完整交易权限必须同时满足可信度达到 60 分、至少一项证件类材料（学生证或校园卡）审核通过、管理员审核通过。
- 学生证或校园卡材料允许脱敏上传，但必须能支持姓名或学号等身份因子判断。
- 校园邮箱验证必须匹配学校配置的合法后缀清单，邮箱验证链接有效期为 30 分钟，且校园邮箱在系统内唯一。
- 学生证或校园卡材料通过审核后，姓名和学号组合应被标记为已占用，其他账号提交相同组合时进入管理员复核。
- 认证因子被驳回后允许重新提交；同一因子 24 小时内最多重提 3 次。
- 校园认证通过后长期有效，不设置固定过期或周期性重审；身份异常举报成立后，管理员可以调整认证状态或限制权限。
- 用户可以申请停用账号；公开资料应隐藏或匿名化，交易、支付、举报、信用和审计事实继续保留。
- 用户可将身份标识切换为校友，校友标签不影响交易权限；系统不要求毕业生主动离场，也不依赖毕业生名单运行。

### 商品、文件与隐私

- 商品禁售范围包括违法违规物品、危险品、药品、烟酒、虚拟账号、作弊资料和代办服务等高风险对象。
- 商品成色采用结构化枚举：全新、几乎全新、轻度使用、明显使用，并允许卖家补充文字说明。
- 商品必须审核通过后才能公开上架。
- 禁售判定以规则服务为主路径，依据关键词字典和禁售分类清单形成规则命中记录；AI 预检标签只作为管理员审核参考。
- 禁售关键词字典和禁售分类清单由超级管理员维护，变更必须记录操作人、时间和变更内容。
- 商品图片在商品公开上架后可以公开访问；私信图片、认证材料、举报证据、申诉材料和支付异常材料默认私有。
- 交易、支付、结算、退款、评价、信用、举报、申诉、处罚、审核和管理员操作等事实记录长期保留，不做简单物理删除。
- 普通聊天可以在用户侧归档；已关联交易、举报、申诉或审计处理的消息和证据不得因归档而物理删除。
- 管理员查看认证材料、举报证据、申诉材料和私信内容等敏感材料时，必须形成敏感访问日志。

### AI 边界

- AI 只进入商品发布和审核预检链路。
- AI 输入默认限制为商品标题、描述、成色、价格、分类和标签。
- AI 输出只作为发布建议或预检标签，不直接改变商品、订单、举报、处罚或用户状态。
- 规则服务是审核预检主路径；LLM 只作为可选优化项处理短文本语义判断、文本建议和分类标签建议。
- AI 处理保存输入摘要、输出结果、理由、置信度和采纳状态，不把完整模型请求和响应原文作为长期业务事实。
- AI 编排层通过统一 `IntelligenceProvider` 接口适配模拟服务、规则服务和 LLM 服务；具体模型供应商不写入领域契约。
- AI 调用采用异步任务模型，前端通过 WebSocket 接收结果，离线时可轮询任务状态。
- AI 任务 30 秒未返回视为失败，同一任务最多自动重试 2 次；AI 结果生成后 24 小时内未采纳则过期。
- 单个商品的同类发布辅助任务每日上限为 5 次，审核预检由系统提交审核时调用，不计入用户配额。
- 系统提供全局 AI 开关；关闭后前端隐藏 AI 入口，后端返回不可用提示，商品发布、审核、交易和治理流程继续可用。
- AI 服务关闭、LLM 关闭或成本受限时，商品发布、人工审核、交易和治理流程仍必须可用。

### 发现、会话与统计

- 私信实时通道采用 WebSocket；数据库消息记录是唯一事实来源。
- 聊天消息采用 PostgreSQL 持久化表保存，核心表包括会话、消息和消息附件，并通过索引和归档字段支撑查询与用户侧归档。
- 私信支持文本、图片和系统卡片；私信图片通过文件存储层保存，并以会话消息附件方式关联。
- 系统卡片由后端生成并作为会话消息持久化，前端只渲染卡片并触发卡片定义的动作，不能伪造卡片。
- 消息必须先持久化再实时推送；WebSocket 推送失败不能导致消息丢失。
- 推荐采用可解释规则和统计排序，使用商品特征、浏览、搜索、分类点击、收藏、下单、成交、评价和卖家信用等数据。
- 推荐不得使用私信正文、举报材料、申诉材料、认证材料或身份隐私资料。
- 商品搜索采用 PostgreSQL 全文检索、`pg_trgm` 模糊匹配和常规索引，不引入独立搜索服务作为目标依赖。
- 地点发现采用校园地点字典和地点筛选，不做实时定位、附近的人或真实地理轨迹能力。
- 站内通知是交易状态、审核结果和治理处理的正式通知渠道；邮箱只作为账号安全或重要提醒的补充渠道。
- 浏览、搜索和点击明细只为推荐、统计和风控保留必要周期，超过周期后转为聚合统计或删除明细。
- 后台统计以 PostgreSQL 视图、索引和聚合查询为主；重统计可用物化视图或定时刷新表，但统计结果不能反向成为业务事实。

### 订单、支付、退款与评价

- 买家创建订单时，系统必须在同一事务或等价原子操作中确认商品仍在售、冻结订单金额并占用商品；同一商品同一时刻最多只能存在一个占用性订单。
- 商品标价是挂牌价；买家下单时可以使用协商价，卖家确认订单表示接受该订单冻结金额。
- 协商价必须来自会话中的已接受议价卡片；聊天文本中的口头价格不作为订单冻结金额来源。
- 同一会话允许多次议价，以最后一次已接受议价卡片为准；订单生成后，该订单关闭前不允许继续为同一商品发起新议价。
- 订单冻结金额是支付、托管、结算、退款和统计的金额来源；支付单金额必须来自订单冻结金额。
- 卖家确认前如需改价，应拒绝当前订单并由买家按新金额重新下单；卖家确认后不直接修改订单冻结金额。
- 面交地点以校园地点字典为基础，支持补充具体位置描述。
- 面交确认码可以作为辅助凭证，但不能单独触发卖家结算。
- 面交进行中不引入独立订单状态；已支付待面交覆盖约定后尚未完成的面交阶段，临时出发、到达或开始面交只作为会话卡片、通知或状态历史事件。
- 在线支付采用担保式交易。支付成功表示资金进入托管状态，不表示卖家已收款。
- 系统不提供平台余额或钱包；每笔订单独立形成支付、托管、退款和结算记录。
- 卖家首次提交商品审核前必须绑定收款方式；模拟支付环境使用模拟收款账户，真实支付适配器接入后映射到对应支付渠道。
- 收款方式作为独立对象管理，同一卖家可绑定多个收款方式，但同一时刻只有一个默认收款方式。
- 订单创建时保存卖家当时默认收款方式的订单级快照，作为争议溯源事实，不因卖家更新收款方式而改写。
- 结算记录表达一笔订单的结算生命周期；每次结算执行或重试形成独立结算尝试，并保存尝试时卖家当前收款方式的尝试级快照。
- 结算成功表示资金从托管账目划入卖家收款方式对应的已结算累计项；系统不提供提现操作。
- 结算失败必须形成管理员处理任务；管理员可在卖家更新收款方式后发起新的结算尝试，新尝试使用新的尝试级收款方式快照。
- 支付渠道采用模拟支付渠道作为正式运行能力，并保留真实支付适配器接口；模拟渠道必须覆盖支付创建、回调、幂等、托管、结算和退款状态。
- 买家确认完成是卖家结算主触发；卖家可在约定面交时间后发起完成确认请求。
- 卖家完成确认请求创建后，买家确认窗口为 48 小时；系统立即通知买家，并在请求创建后 24 小时提醒一次。
- 确认窗口内存在有效退款申请、纠纷、订单相关举报处理或管理员冻结时，系统不得触发超时确认。
- 订单进入已完成待结算后保留 7 天结算冻结期；冻结期内托管资金不划拨，交易任一方可发起常规退款。
- 冻结期到期且无有效退款、纠纷、订单相关举报处理或管理员冻结时，系统自动推进卖家结算；结算成功后订单进入已完成。
- 退款支持全额退款和部分退款。退款金额基于订单冻结金额、支付单金额、已支付金额、已退款金额、托管未结算金额和处理结论计算。
- 卖家可以同意退款；双方存在争议时，由管理员基于交易和治理材料裁决。
- 部分退款不修改订单冻结金额或支付单金额；卖家可结算金额按支付金额扣除已完成退款金额计算。全额退款完成后，相关支付单不得再进入卖家结算。
- 全额退款且订单关闭时，不开放双方评价入口；部分退款后订单仍完成并进入卖家结算时，允许双方在订单完成后评价。
- 买家或卖家在订单进入已支付待面交前主动放弃订单时，订单进入已取消；系统因超时、异常、全额退款或管理员动作结束订单时，订单进入已关闭。
- 已支付订单不能由买卖双方直接取消，只能通过退款、纠纷或管理员处理结束。

### 信用与治理

- 信用采用可解释变动记录聚合，不对普通用户展示单一黑箱信用分。
- 对外信用呈现使用维度摘要和具名行为标签，例如履约率、准时面交次数、最近评价、申诉记录、按时完成面交或缺席约定等。
- 对内可以保留数值或等级，用于排序、风控阈值和审计；数值或等级变化必须落在可追溯的信用记录中。
- 完成交易、结构化评价、履约事实、举报成立、处罚记录、纠纷责任和申诉结果可以触发信用记录。
- 评价采用 1-5 星整数评分、预设标签和可选文本；买卖双方各评价一次，双方都提交或评价窗口关闭后再公开。
- 评价提交后 72 小时内可修改，不支持用户主动撤销；举报成立后管理员可将评价隐藏并排除出信用聚合。
- 退款金额、评价文本、私信内容、AI 预检标签和未成立举报不能直接改变信用。
- 申诉通过、处罚撤销或人工修正时，应追加补偿性信用记录，而不是覆盖历史信用事实。
- 举报人对被举报方默认匿名；同一举报人对同一对象 24 小时内重复提交应合并处理。
- 举报成立触发处罚记录与信用变化，未成立不影响被举报方信用；恶意举报累计达到治理阈值后可限制举报权限。
- 管理员是认证、商品审核、举报处理、申诉复核和权益影响动作的最终裁决者。
- 内容管理员负责日常审核、举报处理、退款争议协助和申诉材料整理；超级管理员负责角色配置、系统配置、敏感审计和严重处罚复核。
- 商品下架、用户限制、处罚记录、信用扣分和申诉复核结论必须由管理员动作触发并留痕。
- 处罚类型包括警告、商品下架、限制发布、限制交易、认证失效和账号禁用；处罚必须记录原因、依据、处理人和时间。

### 时间窗口

- 卖家确认订单时限为 24 小时；超时关闭订单、释放商品占用并通知双方。
- 买家支付时限为卖家确认后 24 小时；超时关闭有效支付单、关闭订单并释放商品占用。
- 订单进入已完成待结算后的常规退款申请入口开放 7 天；窗口内已发起退款继续处理并阻断自动结算，窗口到期无阻断时自动结算，已结算争议进入申诉与人工处理。
- 卖家响应退款申请时限为 48 小时；超时未拒绝视为同意退款。
- 评价开放窗口为订单完成后 14 天；评价修改窗口为提交后 72 小时。
- 消息撤回时限为发送后 2 分钟；系统卡片不可撤回。
- 议价卡片有效期为 24 小时；浏览、搜索和点击明细保留 90 天后转为聚合统计或删除明细。

### 并发与一致性

- 商品占用使用 PostgreSQL 行级锁保护：锁定商品记录，校验在售且无活跃占用订单后，在同一事务内插入订单并更新商品占用状态。
- 商品记录保留当前占用订单引用，与订单状态形成双向校验；占用释放时同步清空。
- 定时任务包括支付超时关闭、完成确认超时、结算冻结期到期、退款超时同意、AI 任务超时、文件清理等，必须幂等执行。
- 目标运行口径为单实例模块化单体；多实例扩展时，关键定时任务和关键状态推进使用 PostgreSQL advisory lock 或等价机制保证同名任务串行。
- 支付回调基于支付单和回调流水号去重，重复回调直接返回成功且不重复处理。
- 跨模块的最终一致场景可以通过领域事件异步处理，但必须保留补偿入口。

### 安全、配置与运行

- 密码使用 bcrypt 或 Argon2id 等安全算法加密存储，数据库不保存明文。
- 同一账号连续登录失败达到阈值后锁定一段时间；同一 IP 高频失败触发验证码或限流。
- Cookie 登录态启用 CSRF 防护；前端默认转义用户输入，服务端过滤富文本白名单。
- 服务端会话记录最后活跃时间；受保护请求隐式滑动续期，默认闲置 7 天失效、绝对 30 天强制重新登录；会话状态探针只返回当前用户和登录态，不签发新 token。
- 文件上传必须校验大小、MIME 类型和文件头，图片字段拒绝可执行格式。
- 公网部署强制 HTTPS，开启 HSTS，不接受 HTTP 明文回退。
- 初始超级管理员、学校信息、校区院系、邮箱后缀、商品分类标签、校园地点字典、举报类型、处罚类型和禁售词典通过种子脚本初始化。
- 系统配置表保存业务阈值和时间窗口，超级管理员调整配置时必须记录变更前后值、操作人和时间。
- 数据库执行每日全量备份和 WAL 增量备份，订单、支付、结算、退款、信用、治理和审计等关键数据需要重点校验。
- 用户首次注册必须同意用户协议和隐私政策，系统记录同意时间、版本号和 IP。

## 正式边界

本项目覆盖校园内 C2C 二手交易闭环，并包含担保式在线支付、支付状态同步、结算和退款处理。以下内容不进入正式目标边界：

- 快递物流、跨城配送和商业化寄卖。
- 多学校商业运营、商家入驻和广告投放。
- 让外部学校统一身份认证成为系统运行前提。
- 真实微信、支付宝或银联商户入网、真实资金清算和公网支付回调部署。
- 面向多商户平台的复杂分账、批量结算和财务清算系统。
- 让 AI 自动下架商品、自动封禁用户或自动裁决申诉。
- 原生 App、小程序或多端统一发布。

## ADR 粒度

ADR 只记录会改变长期架构、模块边界、核心状态机、资金链路、治理链路、AI 使用边界、核心领域对象或关键一致性约束的分叉决策。

单个字段名、页面交互、接口路径、提示文案、局部校验顺序、提醒样式和可由本基线推导出的普通规则，不再单独创建 ADR。

历史访谈形成的细粒度 ADR 已被本文件吸收，保留在 `docs/adr/archive/` 作为来源记录，不作为正式阅读入口。

## 产品口径

正式口径是：

> 一个以校园认证为信任基础、以担保式在线支付和线下面交为交易场景、以 AI 商品发布助手和审核预检为辅助能力、以评价信用和平台治理为闭环保障的校园二手交易系统。

系统数据模型负责保存事实、约束状态和追溯历史；业务流程负责让这些数据形成真实交易闭环；AI 能力负责改善商品发布质量并降低审核压力。
