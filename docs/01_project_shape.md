# 产品目标形态

本文件从产品视角描述校园二手交易系统的唯一目标形态：以校园认证建立交易信任，以商品发现、站内协商、担保/托管式支付、面交确认、结算退款、评价信用和治理留痕构成完整闭环，并以按需调用的 AI 发布辅助提升发布与审核效率。

本文只写稳定形态。更细的长期规则以 `00_project_baseline.md` 为准，领域对象和接口边界以 `02_domain_contracts.md` 为准。

## 产品原则

- 校园认证是交易权限和信用呈现的入口。
- 系统按单校部署设计，学校、校区和院系作为配置数据维护。
- 商品、会话、订单、支付、退款、评价和治理共享同一事实链。
- 在线支付采用担保/托管式交易口径：买家支付后资金先进入托管，卖家收款以结算记录为准。
- AI 是发布与审核预检的按需辅助能力，规则服务是主路径，LLM 是可选优化项。
- 推荐、信用、治理和统计必须能解释来源，不使用无来源的黑箱结论。
- 页面能力服务真实校园交易，而不是只围绕数据库表形成表单。

| 入口 | 面向用户 | 核心目标 |

## 主业务链路

| 链路 | 稳定形态 |
| --- | --- |
| 校园认证 | 用户提交姓名学号、院系、邮箱、学生证或校园卡等因子；系统累积可信度；达到审核线后进入管理员审核；达到完整交易线且审核通过后开放发布、私信、下单、支付、评价和申诉等权限。 |
| 商品发布 | 认证学生创建草稿、上传图片、填写商品信息；可按需调用 AI 发布辅助；提交后由规则记录和管理员审核共同形成上架结论。 |
| 商品发现 | 游客和用户通过分类、搜索、筛选、推荐和详情页发现商品；推荐结果呈现主要来源。 |
| 会话协商 | 买卖双方围绕商品建立会话，支持文本、图片和系统卡片消息；消息先持久化再实时推送，离线和重连通过接口补偿。 |
| 下单占用 | 买家创建订单时原子确认商品在售、冻结订单金额并占用商品；协商价来自已接受议价卡片；同一商品同一时间只允许一个占用性订单推进。 |
| 支付托管 | 卖家确认订单后开放支付入口；支付单金额来自订单冻结金额；支付成功后资金进入托管状态。 |
| 面交完成 | 买家主动确认完成，或卖家在约定面交时间后发起完成确认请求；无有效争议时可按确认窗口规则进入完成待结算。 |
| 卖家结算 | 订单完成待结算后生成结算记录；结算成功才表示卖家收款。 |
| 退款处理 | 已支付未结算订单支持全额退款和部分退款；退款金额不改变订单冻结金额，责任归属由治理记录表达。 |
| 评价信用 | 订单完成后开放评价；评价由星级、标签和可选文本组成；信用变化来自完成事实、结构化评价、治理责任、处罚、申诉和人工修正。 |
| 举报申诉 | 用户可举报商品、留言、消息、订单或账号；管理员处理后，被处理用户可申诉复核。 |
| 统计审计 | 后台基于事实记录形成统计视图；管理员操作和敏感材料访问必须留痕。 |

## 能力边界

### 身份与信用

- 校园认证采用 100 分可信度：姓名学号 40 分，院系信息 10 分，校园邮箱 10 分，学生证或校园卡 40 分。
- 可信度达到 50 分进入管理员审核队列；达到 60 分且审核通过后开放完整交易权限。
- 校园认证通过后长期有效；身份异常举报成立后，管理员可以撤销认证或限制权限。
- 用户公开页不暴露姓名、学号、手机号和认证材料。
- 信用摘要由信用记录聚合得到，不直接覆盖最终分值。

### 交易与资金

- 商品标价是挂牌价；订单冻结金额可以来自买卖双方确认的协商价。
- 协商价以会话中的已接受议价卡片为准。
- 订单创建时冻结交易金额；支付单金额只能读取订单冻结金额。
- 商品当前标价、订单冻结金额、支付单金额、退款金额和结算金额是不同事实。
- 支付成功表示资金托管，不表示卖家已收款。
- 系统不提供平台余额或钱包。
- 卖家提交商品审核前必须绑定收款方式，结算记录保存收款方式快照。
- 全额退款完成后相关支付单不进入卖家结算；部分退款后卖家可结算金额按已支付金额扣除已完成退款金额计算。

### AI 与规则

- AI 输入限制为商品标题、描述、成色、价格、分类和标签等短上下文。
- AI 输出只作为发布建议或审核预检标签，不自动处罚、下架、封禁、扣信用或裁决申诉。
- 每次 AI 或规则处理形成任务记录和结果记录，保存理由、置信度、预检标签和采纳状态。
- 规则服务是默认路径；LLM 关闭或成本受限时，发布、审核、交易和治理流程仍可运行。

### 推荐与隐私

- 商品搜索使用 PostgreSQL 全文检索、`pg_trgm` 模糊匹配和常规索引。
- 推荐可以使用商品特征、浏览、搜索、分类点击、收藏、下单、成交、评价和卖家信用。
- 推荐不得读取私信正文、举报材料、申诉材料、认证材料和身份隐私资料。
- 地点能力基于校园地点字典和地点筛选，不做实时定位或附近的人。
- 私信图片作为会话消息附件保存，默认只对会话参与者和职责范围内管理员可见。
- 系统卡片由后端生成并作为会话消息持久化，前端不能伪造系统卡片。
- 管理员访问认证材料、举报证据、申诉材料、私信内容等敏感材料时，必须记录访问人、目标、原因、时间和结果。

## 工程形态

- 后端采用 Spring Boot。
- 后端采用模块化单体。
- 前端采用 React。
- 数据库采用 PostgreSQL。
- 主接口采用 REST JSON，实时消息采用 WebSocket。
- 聊天消息使用 PostgreSQL 持久化表保存，会话、消息和消息附件通过索引支撑查询。
- 文件存储采用 MinIO 或 S3 兼容对象存储。
- 系统部署在公网云服务器，通过 Docker Compose 编排后端、前端、数据库和文件存储依赖。
- 公网部署配置域名和 HTTPS。
- 登录态通过 HttpOnly Cookie 承载，WebSocket 握手复用同一登录态。
- 后端和前端可部署组件均提供 Dockerfile。
- 运行配置通过环境变量或外部配置注入，镜像不固化环境密钥。
