# 最终质量标准

本文件定义校园二手交易系统达到目标形态时应满足的检查项。它用于判断系统是否形成真实校园可信交易闭环，而不是只形成若干表单、接口和数据库表。

## 产品闭环

- [ ] 用户能完成注册、登录、校园认证因子提交、可信度查询和认证状态查询。
- [ ] 校园认证按姓名学号 40 分、院系信息 10 分、校园邮箱 10 分、学生证或校园卡 40 分累积可信度。
- [ ] 可信度达到 50 分后进入管理员审核队列；完整交易权限必须同时满足可信度达到 60 分、至少一项证件类材料审核通过和管理员审核通过。
- [ ] 校园邮箱验证匹配学校后缀清单，邮箱在系统内唯一；学生证或校园卡通过审核后，姓名和学号组合不得被其他账号直接复用。
- [ ] 校园认证通过后长期有效；身份异常举报成立后，管理员能调整认证状态或限制交易权限。
- [ ] 认证学生能发布商品，并可按需调用 AI 标题优化、描述补全、分类修正、标签建议和审核预检。
- [ ] 商品必须经过审核后进入公开可见状态。
- [ ] 买家能通过搜索、分类、筛选、推荐和商品详情发现商品。
- [ ] 买卖双方能围绕商品建立站内会话，发送文本、图片和系统卡片消息，并保留消息历史。
- [ ] 私信新消息、会话更新、未读数和已读状态能通过 WebSocket 向在线用户实时推送。
- [ ] 消息必须先持久化再实时推送，推送失败不能造成消息丢失。
- [ ] 聊天消息能通过 PostgreSQL 会话、消息和消息附件表按会话、参与者和时间范围查询。
- [ ] 系统卡片由后端生成并持久化，前端不能伪造议价、订单、支付、退款或完成确认卡片。
- [ ] 用户能举报商品、留言、消息、订单或账号；管理员能处理举报；被处理用户能发起申诉。

## 交易资金链

- [ ] 买家创建订单时，系统能原子占用商品并冻结订单交易金额。
- [ ] 同一商品同一时间只能存在一个占用性订单。
- [ ] 商品占用通过 PostgreSQL 行级锁或等价原子机制保护，并与当前占用订单引用双向校验。
- [ ] 协商价来自会话中的已接受议价卡片，聊天文本价格不能直接成为订单冻结金额。
- [ ] 卖家拒绝、买家取消、支付超时、订单关闭或未结算退款完成时，系统能释放商品占用。
- [ ] 卖家确认订单后才开放支付入口，且支付单金额来自订单冻结金额。
- [ ] 模拟支付渠道能完成支付创建、支付回调、幂等处理和托管状态流转。
- [ ] 系统保留真实支付适配器接口，业务层不直接依赖具体支付供应商。
- [ ] 买家付款后资金进入托管状态，支付成功不直接表示卖家已收款。
- [ ] 卖家提交商品审核前必须绑定收款方式；订单保存下单时默认收款方式快照；每次结算尝试保存尝试时收款方式快照。
- [ ] 买家确认交易完成后，订单进入已完成待结算状态，系统能生成待结算记录并设置 7 天结算冻结期。
- [ ] 卖家能在约定面交时间后发起完成确认请求，买家确认窗口为 48 小时。
- [ ] 系统能在完成确认请求创建时立即通知买家，并在请求创建后 24 小时提醒一次。
- [ ] 买家在确认窗口内未响应且无有效退款、纠纷、订单相关举报处理或管理员冻结时，系统能按超时确认进入已完成待结算状态。
- [ ] 已支付未结算订单在结算冻结期内支持全额退款和部分退款，冻结期内托管资金不划拨。
- [ ] 卖家响应退款申请时限为 48 小时，超时未拒绝视为同意退款。
- [ ] 部分退款不修改订单冻结金额或支付单金额，卖家可结算金额按支付金额扣除已完成退款金额计算。
- [ ] 全额退款完成后，相关支付单不能再进入卖家结算。
- [ ] 结算冻结期到期且无有效退款、纠纷、订单相关举报处理或管理员冻结时，系统能自动发起结算尝试。
- [ ] 已结算订单发生争议时，进入申诉与人工处理记录。

## AI 与治理

- [ ] 商品发布流程存在 AI 发布辅助入口。
- [ ] AI 发布辅助和审核预检按需调用，不要求全天候运行。
- [ ] AI 输入限制为商品标题、描述、成色、价格、分类和标签。
- [ ] AI 输出包含建议正文、理由、预检标签、置信度、来源商品和生成时间。
- [ ] 每次 AI 或规则服务处理都形成智能任务记录，并保存来源商品、输入摘要、任务状态和失败原因。
- [ ] AI 任务采用异步模型，支持超时、重试、配额、过期和全局开关。
- [ ] AI 结果可被用户采纳、忽略或修改；只有已采纳的发布建议才能写回商品草稿。
- [ ] AI 预检标签能进入商品审核记录，但不能自动处罚、下架、封禁、扣信用或裁决申诉。
- [ ] 规则服务是审核预检主路径，LLM 是可选优化项。
- [ ] 模拟 AI 服务、规则服务和 LLM 服务共享同一输出契约。
- [ ] 商品下架、用户限制、处罚记录和信用扣分等权益影响动作必须由管理员裁决并留痕。

## 数据模型与一致性

- [ ] 核心实体覆盖身份、服务端会话、文件、商品、发现、会话、订单、支付、结算、结算尝试、退款、评价、信用、治理、通知、审计、统计和 AI 发布辅助。
- [ ] 商品、订单、支付单、结算记录、结算尝试、退款单、举报、申诉、认证和 AI 结果具备明确状态字段。
- [ ] 订单状态、支付状态、托管状态、结算状态和退款状态变化有可追溯记录。
- [ ] 金额字段使用定点数。
- [ ] 商品删除采用逻辑删除并保留历史关联。
- [ ] 订单创建与商品占用在同一事务或等价原子操作中完成。
- [ ] 订单冻结金额、支付单金额、退款单金额、结算金额、订单级收款方式快照和结算尝试级收款方式快照之间具备可追溯关系。
- [ ] 支付回调按幂等方式处理，重复回调不能重复改变订单或资金状态。
- [ ] 定时任务和支付回调具备幂等保证，重复执行不重复发通知、不重复创建结算记录、结算尝试或退款记录。
- [ ] 同一支付单的累计退款金额不得超过可退金额。
- [ ] 信用变化能记录来源业务、关联对象、变化原因、内部数值或等级变化和记录时间。
- [ ] 后台统计至少覆盖用户数、在售商品数、成交订单数、支付成功率、结算处理、退款处理、分类热度、举报处理和好评率。
- [ ] 后台统计以 PostgreSQL 视图、索引和聚合查询为主，统计结果不反向修改业务事实。

## 文件、隐私与保留

- [ ] 商品图片、认证材料和举报证据的文件二进制不直接存入业务数据库。
- [ ] 文件元数据能记录存储键、访问引用、文件类型、大小、所属业务对象、上传者、审核状态和可见范围。
- [ ] 商品图片审核通过并公开上架后可以公开访问；私信图片、认证材料、举报证据和申诉材料默认私有。
- [ ] 私信图片通过文件元数据关联会话消息，并按会话参与关系控制访问。
- [ ] 用户只能查看自己提交或自己参与对象中的敏感材料。
- [ ] 管理员访问认证材料、举报证据、申诉材料、私信内容等敏感材料时，必须形成敏感访问日志。
- [ ] 交易、支付、结算、退款、评价、信用、举报、申诉、处罚、审核和管理员操作等事实记录长期保留。
- [ ] 普通会话可以在用户侧归档；已关联交易、举报、申诉或审计处理的消息和证据继续作为事实记录保留。

## 推荐与信用

- [ ] 推荐能使用商品分类、标签、价格、成色、地点、浏览、搜索、分类点击、收藏、下单、成交、评价和卖家信用等可解释数据。
- [ ] 商品搜索基于 PostgreSQL 全文检索、`pg_trgm` 模糊匹配和常规索引。
- [ ] 推荐不使用私信正文、举报材料、申诉材料、认证材料或身份隐私资料。
- [ ] 推荐结果能说明主要来源，例如同类商品、近期热门、相近价格、相近地点或高信用卖家商品。
- [ ] 地点发现基于校园地点字典和地点筛选，不保存实时定位轨迹。
- [ ] 订单完成后，双方能互相评价。
- [ ] 全额退款且订单关闭时，不开放双方评价入口；部分退款后订单仍完成并结算时，允许双方评价。
- [ ] 评价包含 1-5 星整数评分、预设标签和可选文本，双方都提交或评价窗口关闭后再公开。
- [ ] 对外信用摘要由维度摘要和具名行为标签组成，不展示单一聚合信用分；对内数值或等级只用于排序、风控和审计。
- [ ] 退款金额、评价文本、私信内容、AI 预检标签和未成立举报不能直接改变信用。
- [ ] 申诉通过、处罚撤销或人工修正时，系统能追加补偿性信用记录。

## 工程运行

- [ ] 后端采用 Spring Boot。
- [ ] 后端采用模块化单体。
- [ ] 前端采用 React。
- [ ] 数据库采用 PostgreSQL。
- [ ] 主接口采用 REST JSON，实时消息采用 WebSocket。
- [ ] 文件存储采用 MinIO 或 S3 兼容对象存储。
- [ ] 登录态通过 HttpOnly Cookie 承载，服务端会话滑动续期并设置闲置上限和绝对上限，WebSocket 握手复用同一登录态，不采用 access/refresh token 刷新体系。
- [ ] 后端和前端可部署组件均提供 Dockerfile。
- [ ] 系统部署在公网云服务器，数据库、后端、前端和文件存储依赖能通过 Docker Compose 形成完整运行环境。
- [ ] 公网部署配置域名和 HTTPS。
- [ ] 运行配置通过环境变量或外部配置注入，不写死在镜像中。
- [ ] 密码加密存储。
- [ ] 公网部署强制 HTTPS，文件上传校验大小、MIME 类型和文件头。
